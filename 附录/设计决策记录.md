# 设计决策记录（ADR）

> 本文记录 `vdot.vv` 自定义指令的关键设计决策、备选方案与取舍理由。
> 用于支撑评审「可行性」「探索性」「创新性」三项评分。
> 决策确认时间：2026-10-30（团队确认 A 组默认值）

---

## ADR-001 指令编码

决定

采用 `custom-0` opcode（`0b0001011` = `0x0B`），R-type 格式：

```
 31      25 24    20 19    15 14  12 11     7 6        0
+----------+--------+--------+------+--------+----------+
| funct7   |  vs2   |  vs1   |funct3|   vd   |  opcode  |
| 0000000  |        |        | 000  |        | 0001011  |
+----------+--------+--------+------+--------+----------+
```

即 `vdot.vv vd, vs1, vs2` = `0x00 <vs2> <vs1> 0x0 <vd> 0x0B`。

预留 `funct7 = 0000001` 作为后续 `vdot.vx`（vs1 为标量整数寄存器）变体。

备选与取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 复用 `OP-V`（`0x57`）的保留 `funct6` | 编码"看起来像"标准向量指令；与 V 扩展指令族连续 | `funct6` 保留位可能被未来 V 标准版本分配；香山/ NEMU 现有的 V 指令解码路径会对未知编码直接报 illegal，扩展时要绕开解码表 | 否 |
| `custom-0`（`0x0B`） | 与所有标准扩展隔离，永不冲突；香山 `DecodeConstants` 中该 opcode 目前为保留空位，实现最干净 | 不属于 V 扩展命名空间，汇编器不认 | **采用** |
| `custom-1/2/3` | 同上 | 无差别 | 保留给后续变体（`vdot.vx`、`vdot4.vv` 等） |

风险：若 RISC-V 官方后续标准化 `vdot` 并给出正式编码，需要做一次编码迁移；本文档中已说明，迁移仅涉及解码表一处。

## ADR-002 结果写回宽度（本题语义歧义的核心）

官方给出的参考语义为 Python 伪代码：

```python
def vdot_vv(vs1, vs2, sew=8):
    result = 0
    for i in range(8):
        result += sign_extend(vs1[i]) * sign_extend(vs2[i])
    vd[0] = result
    vd[1..VLEN-1] = 0
```

问题：`vs1[i]` 是 int8，`result` 的位宽伪代码没有约束。位宽推演：

- 单项乘积范围：`[-128×-128, 127×-127]` → 最大 `16384`，需 16 位有符号承载；
- 8 项累加最坏值：`8 × 16384 = 131072` → 需 18 位有符号（`[-131072, 130050]`）；
- 若 SEW=8 的 `vd[0]` 只能存 8 位，则必须截断或饱和。

| 方案 | 语义 | 优点 | 缺点 |
|---|---|---|---|
| A 低 8 位截断 | `vd[0] = result[7:0]` | 实现最简，硬件零成本 | 信息大量丢失，`vdot` 失去实用价值（点积结果几乎总溢出） |
| B 饱和到 int8 | `vd[0] = sat8(result)` | 保号、无回绕，映射到 int8 激活 | 丢失幅度信息；用于量化推理时精度损失明显 |
| C 32 位写回 | `vd[0]`（按 SEW=32 读）`= sign_extend(result)`，其余元素清零 | **数学无损**；与业界 int8 点积惯例一致（TFLite / Gemmini / 各类 NPU 均为 int32 累加器） | 超出了"SEW=8 元素"的字面约定，需要显式定义读写约定 |

决定：采用 方案 C。

补充约定

1. `vd` 中除 `vd[0]` 的低 32 位外，其余全部清零；
2. 结果的读取方式为"按 `SEW=32` 读取 `vd[0]`"，即 `vdot` 改变了 `vd` 的有效元素宽度——这是本设计对"约简类向量指令"的语义扩展，必须在设计文档中显式声明；
3. 实现上 `result` 在硬件中是 32 位有符号（实际只用到 18 位有效值），高位为符号扩展。

选 C 的实际考虑：A 在真实模型上会静默截断，B 会让相邻求和结果互相影响、不太好解释；C 功能上最干净，位宽推演的推导过程本身也能写成一段设计论证。A/B 在文档里作为对比保留。

## ADR-003 `vtype` 约束

决定：仅当 `SEW=8` 且 `LMUL=1` 时该指令合法；其余组合触发 **illegal instruction** 异常。

理由

- `vdot.vv` 的语义天然绑定 8 位元素（8 项点积 = 8 个字节）；
- `LMUL>1` 时的语义需要额外定义（例如"每组 8 个元素各产生一个结果，写满 `VLEN/32` 个元素"），属于扩展潜力，放在设计文档的"未来扩展"一节，不在本次实现范围内；
- 显式约定"非法"比"静默按某种方式执行"更符合规范设计，也便于 difftest 两侧对齐。

实现位置：香山侧在译码/发射阶段用一个 `vdot_illegal` 条件判断；NEMU 侧在 `vdot` 执行函数入口做相同判断并 `INV()`（触发 illegal instruction）。

## ADR-004 `vl` 与 `vstart` 行为

决定

- `vl ≥ 1`：执行点积并写回 `vd[0]`；
- `vl = 0`：不写回、不 trap（遵循 RISC-V Vector 对零长度向量操作的约定）；
- `vstart ≠ 0`：视为 **illegal instruction**（未实现分段重启）。

理由：约简类指令的简化实现；把"未实现的语义"显式化，避免出现"看起来实现了但边界行为不符合规范"的情况。`vl=0` 的静默无操作是 V 扩展的通行做法，必须实现。

## ADR-005 不修改 LLVM 工具链

决定：不向上游 LLVM 添加 `vdot` 的汇编/内建函数支持，测试程序通过 `.insn` 伪指令直接编码。

```c
// 使用示例（内联汇编封装）
#define VDOT_VV(vd, vs1, vs2)                                        \
  asm volatile(".insn r 0x0B, 0, 0, %0, %1, %2"                      \
               : "=vr"(vd) : "vr"(vs1), "vr"(vs2))
```

理由

- LLVM RISC-V backend 增加自定义 intrinsic 需要重编译整套 LLVM（1–2 小时级），且赛题不要求；
- `.insn` 编码路径完全可控，不引入工具链不确定性；
- 用 C 宏 + 汇编模板封装后，使用体验等价于 intrinsic，可作为"软硬件协同"得分项的补偿材料。

## ADR-006 微架构实现路线（阶段二定稿前的初稿）

决定：优先"并入 `VectorALU` 作为一条新的 ALU op"的最小改动路线，跑通后再考虑独立的 `VDot` 功能单元 + 流水化。

理由

- 香山的向量功能单元已有一条完整的"译码 → IssueQueue → `VFu` → `VectorALU` → 写回"通路，把 `vdot.vv` 作为 `VectorALU` 的一个新 op 可以零新增时序路径地跑通，风险最低；
- 跑通 difftest 之后，再在文档中给出"独立功能单元 + 2 级流水 + 乘法树"的优化版本做延迟/面积对比，这样既有"能跑"的完整性得分，又有"微架构优化"的探索性得分（评分表中「探索性—微架构优化」5 分）。

待定项（阶段二设计文档定稿时给出数据）

1. 乘法树结构：8 个 int8 乘法 → 两两配对加法树（4→2→1）→ 末尾 18/32 位累加；
2. 关键路径估算：int8 乘法 + 3 级加法树；
3. 是否复用 `VectorALU` 的 vs2 读口（当前倾向于复用，避免新增寄存器堆端口）。
