> 目录：`/home/rv/work/xs-env/NEMU`（参考模型）、`/home/rv/work/xs-env/XiangShan`（被测 DUT）
> 状态：已跑通。21,500 条指令 / 74,585 周期的完整测试程序在香山 RTL 与 NEMU 参考模型上逐条比对无差异。

## 1. 为什么必须在 NEMU 侧实现

香山的差分测试（difftest）把 NEMU 编译成动态库 `riscv64-nemu-interpreter-so`，由 RTL 在每个指令退休时把「PC + 指令编码」交给参考模型执行，再逐字段比对体系结构状态（GPR / 向量寄存器 / CSR / 内存写）。

因此：

* 只在 RTL 里实现了 `vdot.vv`，参考模型不认识这条指令 → 第一条自定义指令退休时就会触发
  `different at pc = ...` 或参考模型直接报非法指令；
* 只有 RTL 与 NEMU 两侧语义逐位一致，difftest 才能跑通，这也是本阶段「协同仿真」的验收依据。

## 2. NEMU 侧实现（4 个文件，71 行 diff）

补丁全文见 `3-协同仿真与评估/3.1-NEMU扩展.patch`。

### 2.1 语义实现：`src/isa/riscv64/instr/rvv/vcompute.h`

```c
def_EHelper(vdot_vv) {
  const int vd  = BITS(s->isa.instr.val, 11, 7);
  const int vs1 = BITS(s->isa.instr.val, 19, 15);
  const int vs2 = BITS(s->isa.instr.val, 24, 20);
  int32_t sum = 0;
  int i;
  for (i = 0; i < 8; i++) {
    int8_t a = (int8_t)vreg_b(vs1, i);
    int8_t b = (int8_t)vreg_b(vs2, i);
    sum += (int32_t)a * (int32_t)b;
  }
  for (i = 0; i < VENUM8; i++) {
    vreg_b(vd, i) = 0;
  }
  vreg_i(vd, 0) = (uint32_t)sum;
}
```

要点：

| 点 | 说明 |
| --- | --- |
| 取操作数 | `vreg_b(vsX, i)` 取 `cpu.vr[vsX]._8[i]`，按 8 bit 元素访问；先转 `int8_t` 再乘，保证符号扩展正确 |
| 累加宽度 | 用 `int32_t` 累加，8 项乘积最大 8×16384 = 131,072，32 bit 不会溢出 |
| 写回 | 先把 `vd` 的 16 个 8 bit 元素全部清零（对应 RTL 侧 `vd[VLEN-1:32] = 0`），再用 `vreg_i(vd,0)` 写入低 32 bit —— **与方案 C 的 RTL 行为逐位一致**，这是 difftest 能通过的关键 |
| 无副作用 | 不修改 vl / vtype / vstart / vxsat，不产生异常（`vl=0` 与 `vstart≠0` 的情形在 RTL 侧统一按前置条件排除） |

### 2.2 指令表注册：`src/isa/riscv64/include/isa-all-instr.h`

NEMU 的每条指令都要进 `VECTOR_INSTR_TERNARY` 列表——这个 X-macro 列表同时生成
`EXEC_ID_<name>` 枚举、`table_<name>()` 解码助记符和执行分发入口：

```c
#define VECTOR_INSTR_TERNARY(f) \
  f(vdot_vv) f(vadd) f(vsub) f(vrsub) f(vminu) f(vmin) \
  ...
```

> 只改 `decode.c` 而不加进这张表，会编译失败：
> `error: implicit declaration of function 'table_vdot_vv'`。

### 2.3 译码入口：`src/isa/riscv64/instr/decode.c`

在 `def_THelper(main)` 的 RVV 分支后挂上 custom-0 的模式匹配：

```c
#ifdef CONFIG_RVV
  // CIE-2026 自定义指令 vdot.vv : custom-0 = 0b0001011, funct3 = 000, funct7 = 0
  def_INSTR_TAB  ("0000000 ????? ????? 000 ????? 00010 11",        vdot_vv);
#endif // CONFIG_RVV
```

模式串 32 位逐位对应 `funct7 | rs2 | rs1 | funct3 | rd | opcode`，其中 opcode 的 7 bit 拆成
`00010 11`（= `0x0B`，custom-0）。与 RTL 侧 `BitPat("b0000000??????????000?????0001011")` 完全同构，
保证两侧对「什么编码算 vdot.vv」的判断一致。

## 3. 踩坑记录：参考模型与 RTL 的启动 flash 预设必须一致

现象：换上新编译的参考模型后，difftest 在第 2 条指令就报错并 ABORT：

```
t0 different at pc = 0x0010000004, right= 0x0000000000000001, wrong = 0x0000000080000000
Core 0: ABORT at pc = 0xa98af705c00a
Core-0 instrCnt = 2, cycleCnt = 2,152
```

原因：香山 RTL 侧（`difftest/src/test/csrc/common/flash.cpp`）在没有 `-F` 参数时，会给 flash 填一个
2 条指令的内建 bootrom：

```c
// addiw t0, zero, 1 ; slli t0, t0, 0x1f ; jr t0
flash_dev.base[0] = 0x01f292930010029b;   // addiw + slli
flash_dev.base[1] = 0x00028067;           // jr
```

而新版 NEMU 的 `configs/riscv64-xs-ref_defconfig` 默认给 flash 填的是一个6 条指令的旧预设
（多出 `csrrsi / slli / csrrc` 三条），于是两侧从 PC `0x10000000` 起执行的指令序列就不同，
`t0` 在第 2 条指令处必然分叉。旧版 `ready-to-run/riscv64-nemu-interpreter-so` 没有这段预设逻辑，
所以「开箱即用」，一旦自己重编就会暴露。

修复：把参考模型的预设改成与 RTL 内建 bootrom 完全一致的 3 个 32 bit 字：

```diff
-CONFIG_FLASH_PRESET_CONTENT="0x74446073,0x0010029b,0x02a29313,0x30033073,0x01f29293,0x00028067"
+CONFIG_FLASH_PRESET_CONTENT="0x0010029b,0x01f29293,0x00028067"
```

改完必须 `make riscv64-xs-ref_defconfig` 重新生成 `include/config/auto.conf`，再 `make clean && make -j16`——
**直接改 `.config` 手工 sed 不会生效**（`auto.conf` 不跟着更新，编出来的还是旧配置，这一点我们用
`strings build/riscv64-nemu-interpreter-so | grep 74446073` 验证过）。

另一个坑：`def_EHelper` 里 `BITS(x, hi, lo)` 的参数是 (高位, 低位)。最初写成
`BITS(instr, 7, 11)`（高低颠倒），编译通过但运行时 `vd` 取到负数，参考模型直接
`Assertion 'index >= 0 && index < 32' failed`。
