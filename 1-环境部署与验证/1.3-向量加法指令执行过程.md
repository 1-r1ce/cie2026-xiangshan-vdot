# S1-3 向量加法指令（vadd.vv）执行过程文档

> 阶段一交付物之三。记录在"香山"昆明湖 V2 微架构上的向量加法指令从取指到写回的完整执行过程，
> 全部数据来自本项目的真实运行（Verilator 仿真 + difftest 关闭的裸机程序），非纸面推演。

- 团队：panpan最努力（齐鲁师范学院）
- 平台：XiangShan `MinimalConfig`（昆明湖 V2 微架构，VLEN=128），Verilator 5.052
- 程序位置：`nexus-am/apps/vec-add-xiangshan/`（源码见本仓库 `1-环境部署与验证/源码/vec-add-xiangshan/`）
- 运行日志：`1-环境部署与验证/日志/向量加法运行日志.log`

## 1. 指令定义（RV64V，OPIVV 编码）

被测指令是 RISC-V "V" 扩展的向量-向量整数加法：

```
vadd.vv vd, vs1, vs2
```

编码（`OPIVV`，opcode `0x57`，funct3 = `000`）：

| funct6 | vm | vs2 | vs1 | funct3 | vd | opcode |
|--------|----|-----|-----|--------|----|--------|
| 000000 | 1  | rs2 | rs1 | 000    | rd | 1010111 |

汇编后实测编码（`riscv64-linux-gnu-objdump`）：

```
80000250:  02220357    vadd.vv  v6,v2,v4
```

语义：对每个有效元素通道 `i ∈ [0, vl)`，执行 `vd[i] = vs1[i] + vs2[i]`，元素宽度、分组方式由
`vtype` 决定（本例 `SEW=32`、`LMUL=2`），尾部元素按 `ta/ma` 策略处理（本例不活跃元素不写回）。

---

## 2. 前置状态：`mstatus.VS` 必须打开（本次实测的坑）

RISC-V 规定：当 `mstatus.VS = Off`（值为 0）时，任何向量指令都视为非法指令。
香山仿真环境下的裸机程序（nexus-am）启动时 `mstatus` 为 `0x6000`，即 VS=Off，此时执行
`vsetvli` 会在后端永久停摆——指令不提交、不产生异常打印，`instrCnt` 冻结在 375，仿真器一直空转到周期上限。
这是本项目踩到的第一个真问题，根因与模型、difftest、flash 加载均无关，纯粹是特权态状态位未使能。

解决：进入向量代码前把 `mstatus.VS`（bit 10:9）置为 `01b`（Initial）：

```
[0] mstatus = 0x6000 (VS field = 0)
    置 VS=Initial 后 mstatus = 0x6600 (VS field = 3)
```

> 注：写入 `0x600` 后 `0x6600` 的 VS 字段读出为 3（Dirty），因为硬件把"向量寄存器已被修改"标记为 Dirty，
> 符合规范（写 Initial 后一旦有向量 regfile 写入即升为 Dirty）。

---

## 3. 向量长度配置：`vsetvli`

```
vsetvli zero, a5, e32, m2, ta, ma     # 80000234
```

| vtype 字段 | 值 | 含义 |
|-----------|----|------|
| SEW | 32 | 元素宽度 32 bit |
| LMUL | 2 | 寄存器分组倍数 |
| ta | 1 | 尾部元素不写回（tail agnostic） |
| ma | 1 | 掩码关闭的通道不写回（mask agnostic） |

实测 VLMAX 与 VLEN 的关系（`VLEN = 128`）：

```
[1] vsetvli zero, e32, m1  -> vl=4  => VLEN = 128 bit
    vsetvli zero, e32, m2  -> vl=8  (VLMAX 随 LMUL 翻倍)
```

即 `VLMAX = VLEN/SEW × LMUL = 128/32 × LMUL`：`m1 → 4`，`m2 → 8`。
后续加法使用 `LMUL=2` 以便一次覆盖 8 个元素（`v2/v3`、`v4/v5`、`v6/v7` 各为 256 bit 的寄存器组）。

---

## 4. 完整指令序列与地址

```asm
80000234:  0d17f057   vsetvli     zero,a5,e32,m2,ta,ma   ; 配置 vtype/vl
80000240:  02046107   vle32.v     v2,(s0)                 ; 装入 va[0..7]
8000024c:  0204e207   vle32.v     v4,(s1)                 ; 装入 vb[0..7]
80000250:  02220357   vadd.vv     v6,v2,v4                ; 逐元素 32 位加法
8000025c:  020ae327   vse32.v     v6,(s5)                 ; 存回 vc[0..7]
80000260:  0ff0000f   fence                                ; 保证存储对后续标量读取可见
```

结果核对（程序自身输出）：

```
[3] 输入 va = {1,2,3,4,5,6,7,8}
    输入 vb = {10,20,30,40,50,60,70,80}
    向量结果 vc = {11,22,33,44,55,66,77,88}
[4] 标量参考 = {11,22,33,44,55,66,77,88}
    vadd.vv 与标量加法一致性: PASS
[5] vmv.x.s 读 v6 lane0 = 11 (期望 11)；vslidedown 后读 lane0 = 88 (期望 88)
```

`vmv.x.s` / `vslidedown.vx` 的读回同样正确，说明数据确实落在向量寄存器 `v6`（LMUL=2 时占 `v6/v7`）中，
而不是仅靠内存侧"看起来对"。

## 5. 微架构执行过程（昆明湖 V2）

向量指令与标量指令共用前端，但在后端走独立的向量执行通路，整体分为五段：

① 取指与译码
- `vsetvli` 与 `vadd.vv` 由前端取入 ICache，进入 `Decode`。
- 分支/预译码阶段按 opcode 判为向量指令（`opcode[6:2] = 10111`），转交 `VecDecoder` 展开。
- `VecDecoder` 把 32 bit 指令映射成 `FuType`/`FuOpType` 与 `UopSplitType`：
  - `vsetvli` → `FuType.vsetvl` 类，单独的功能单元处理，负责更新 `vtype`/`vl`；
  - `vadd.vv` → `FuType.vipu`（向量整数 ALU，VIPU）。
- 译码同时读取 `vtype` 得到 `SEW/LMUL`，判断是否需要微指令拆分（当 `VLMAX` 超过硬件数据通路宽度
  需要多拍；本例 `VLEN=128`、`SEW=32`，`LMUL=2` 共 8 元素可一次走完）。

② 重命名与派发
- 向量寄存器 `vd/vs1/vs2` 在 `Rename` 中映射到向量物理寄存器堆（VfPreg，`MinimalConfig` 为 160 项）。
- 重命名还处理"向量寄存器组"语义：`LMUL=2` 时 `v6` 对应 `v6,v7` 两个物理寄存器，`vd` 被标记为整组写。
- 派发阶段将 uop 送入 向量发射队列（实测构建中的实例名
  `IssueQueueVfmaVialuFixVimacVppuVfaluVfcvtVipuVsetrvfwvf`，说明 Vipu 与 Vialu/Vfma/Vsetvl 等共用一个调度器）。

③ 发射与读寄存器
- 发射条件：源操作数就绪（向量 regfile 读端口）、目标写口可用、`vtype` 相关的配置已建立。
  向量指令间存在 `vconfig` 唤醒链（配置类指令唤醒依赖它的向量操作），这也是 `vsetvli` 必须先于
  `vle32.v` 发射的原因。
- 读出的 `vs1`、`vs2` 各为 256 bit（LMUL=2）数据，连同 `vm/vstart/vl/vxrm/vlmul` 等控制信息一起送进 VIPU。

④ 执行：VIPU / VIAlu
- 实现位置：`src/main/scala/xiangshan/backend/fu/wrapper/VIPU.scala`（`VecPipedFuncUnit` 子类），
  内部实例化 `yunsuan.vector.alu.VIAlu`（`yunsuan` 子模块里的向量 ALU）。
- 数据通路宽度 `dataWidthOfDataModule = 64`，模块数 `numVecModule = VLEN/64 = 2`，即 128 bit 一拍算 2 个
  64 bit 子模块；`vadd.vv` 的运算由 `VAluOpcode` 中选择加法操作完成。
- 加法本身组合逻辑延迟低（整数 32 位加法），瓶颈在读写 regfile 与流水握手；本例 `LMUL=2` 需要跨两个
  data module 顺序处理，因此 `vadd.vv` 的有效延迟表现为数拍。

⑤ 写回与提交
- 结果 `io.out.bits.res.data` 写回向量 regfile 对应物理寄存器组；随后 `vse32.v` 从 regfile 读出并写入 DCache。
- 向量指令按程序序提交（本例无异常、无 `vstart` 部分恢复），最后 `fence` 保证向量存储对后续标量 load 可见。
- 同时 `mstatus.VS` 由 Initial 提升为 Dirty（见第 2 节输出 `0x6600`）。

## 6. 实测周期数据

| 段 | 说明 | 周期 |
|----|------|------|
| 向量段（`vsetvli` + 2×`vle32.v` + `vadd.vv` + `vse32.v` + `fence`） | 8 个元素完整装入-相加-存储 | **201 周期**（retires 51 条指令） |
| 标量对照（8 次 `acc += va[i]+vb[i]`） | 同样 8 个元素的加法累加 | 152 周期 |
| 全程序 | `instrCnt = 40,691`，`cycleCnt = 116,764`，IPC = 0.348489 | — |

结论与解读：
- 单看"8 个元素相加"这一件事，向量指令并没有比标量循环更快——这符合预期：本例 `VLEN=128` 很小，
  而向量段还额外承担了 2 次 gather 式载入、1 次存储和一次 `fence`，且 `201` 周期含冷启动
  （首次触达向量 regfile、`vconfig` 唤醒链建立）开销。
- 向量的优势在元素数远超 VLEN 的循环上体现（摊薄 `vsetvli` 与配置开销，每拍处理 `VLEN/SEW×LMUL` 个元素）；
  这也是本项目阶段二要做的 `vdot.vv`（8 元素点积归约为一个结果）需要重点论证"何时值得用"的原因。
- 该数据同时给出了本项目后续迭代的成本基线：仿真速度约 575–640 周期/秒（`116,764` 周期 ≈ 181–342 秒），
  一次完整回归 3–6 分钟，这直接决定了 vdot 的设计-验证节奏（见 `docs/tech/仿真速度问题排查报告.md`）。

## 7. 复现步骤

```bash
# 1) 编译裸机程序（带 V 扩展）
source /home/rv/work/xs-build-env.sh
cd $AM_HOME/apps/vec-add-xiangshan
make ARCH=riscv64-xs MARCH=rv64gcv CROSS_COMPILE=riscv64-linux-gnu-

# 2) 在香山 emu 上运行
cd /home/rv/work/xs-env/XiangShan
./build/emu --no-diff -i $AM_HOME/apps/vec-add-xiangshan/build/vec-add-xiangshan-riscv64-xs.bin \
            -C 400000 --force-dump-result
```

要点：
- `MARCH=rv64gcv` 必须显式传给 make（nexus-am 默认 `rv64gc`，不带 V，汇编器会拒绝 `vadd.vv`）。
- `--no-diff` 关闭 difftest：参考模型 `riscv64-nemu-interpreter-so` 对向量指令支持不完整，开启会误报不匹配。
- `-C` 给足周期上限（本例取 400000，实际用 116764）。

## 8. 与阶段二 `vdot.vv` 的关系

本交付物同时是阶段二的基线与方法论：
- `vadd.vv` 走的通路（`VecDecoder → FuType.vipu → VIPU/VIAlu → 向量 regfile`）就是 `vdot.vv` 要复用的通路，
  阶段二将在 `VipuType` 中新增 `vdot_vv` 操作码并在 VIPU 内旁路出乘累加逻辑，避免新开向量功能单元带来的
  派发/唤醒大改（决策见 `docs/tech/设计决策记录.md` ADR-002/003）。
- 本节测得的 201 周期/8 元素与 575 周期/秒的仿真速度，是阶段三加速比论证的对照组数据。
- `mstatus.VS` 这一坑已写入阶段一测试清单：任何含向量指令的测试程序都必须先使能 VS，否则会表现为静默停摆。
