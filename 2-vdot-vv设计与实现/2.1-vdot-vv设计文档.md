## 1. 赛题背景与本设计的定位

大语言模型推理中的"量化权重 × 量化激活"（W8A8）在数学上是一个短向量点积：
每 8~32 个 int8 元素做一次乘累加，得到一个 int32 部分和。通用向量 ISA 只能用 `vmul`+`vredsum`
两步完成，或者退化为标量循环；前者需要两条指令、两个节拍段，后者完全浪费向量通路。

`vdot.vv` 把"8 元素 int8 点积"压成**一条指令、一次执行、结果直接落在 `vd[0]`**，这正是
赛题"面向边缘 AI 大语言模型推理"的核心痛点：减少指令数、减少向量寄存器压力、便于后续扩展到
int4·int8 混合精度。

## 2. 指令语义（本项目定义）

```
vdot.vv vd, vs1, vs2
```

对 `i = 0 .. 7`：

```
prod_i  = sext8(vs1[i]) * sext8(vs2[i])        // 每个乘积 16 bit 有符号（范围 ±16384）
vd[0]   = sign-extend32( Σ prod_i )            // 结果 32 bit，写入 vd 的低 32 位
vd[1..VLEN-1] = 0                              // 其余位清零
```

补充约定：

| 项 | 约定 |
| --- | --- |
| 元素宽度 | 仅 `SEW=8`（`vtype` 为 e8）有意义；`LMUL=1`，取 `vs1/vs2` 的低 64 bit（8 个元素） |
| 写回宽度 | 32 bit（ADR-003 方案 C），覆盖 `vd[0]` 的 4 个字节，其余位清零 |
| `vl` | 至少为 8；`vl<8` 时未定义（当前实现仍按 8 个元素计算） |
| 掩码 | 不使用掩码（`vm=1`）；`vm=0` 时忽略掩码，仍对 8 个元素求和 |
| 旧 `vd` | 不读取（`vdRen = F`），指令不依赖目标寄存器旧值 |
| 异常 | 仅 `illegalInstr`（由 VIPU 的 `exceptionOut` 统一提供） |

## 3. 指令编码

按 ADR-001 采用 custom-0 空间，避免与 RVV 官方 `vdot`(Zvdot4a8i) 等未来标准指令冲突：

| funct7 | rs2 | rs1 | funct3 | rd | opcode |
| --- | --- | --- | --- | --- | --- |
| `0000000` | `vs2` | `vs1` | `000` | `vd` | `0001011` (custom-0 = 0x0B) |

GNU as 2.42 尚不认识该助记符，且 `.insn r` 的 rd/rs1/rs2 只接受通用寄存器（传 `v3,v1,v2` 会报
`illegal operands`），因此测试程序直接写编码字：

```c
__asm__ volatile(".word 0x0020818B");   /* funct7=0 | vs2=v2 | vs1=v1 | funct3=0 | vd=v3 | 0x0B */
```

（编译器端不改 LLVM，符合赛题"只需 RTL + 仿真"的边界。）

## 4. 为什么落在 VIPU（设计取舍）

香山后端已经有一批向量功能单元（`FuType.vialuF` / `vipu` / `vimac` / `vppu` / `vset` / `vldu` …）。
`vadd.vv` 这类逐元素运算走 `VialuFix`，而归约类（`vredsum.vs`、`vredmax.vs`、`vcpop.m`、
`viota.m`、`vmv.x.s`）走 `VIPU`。`vdot.vv` 本质是"短向量归约成单元素"，与 `vredsum` 同族，因此：

| 方案 | 改动面 | 结论 |
| --- | --- | --- |
| A. 新开一个 `FuType.vdot` 功能单元 | 需改 `FuType`、`FuConfig`、译码、发射队列、rename 的 FU 枚举、每个 Config 的 FU 列表 | 改动大、回归风险高，否决 |
| **B. 复用 `FuType.vipu`，新增 `VipuType.vdot_vv`，在 VIPU 内旁路出点积通路** | 3 个文件、约 15 行 | **采用**（ADR-002） |
| C. 挂在 `Vimac` 上，用现有乘累加器 | 受 `Vimac` 的 element-wise 语义与 lane 绑定约束，需加归约网络 | 复杂度反而更高，否决 |

复用 VIPU 的额外好处：发射队列、rename 的源/目的寄存器组处理、写回端口、`vconfig` 唤醒链全部复用，
`vdot.vv` 立刻就能享受"依赖 `vsetvli` 的唤醒"和"向量 regfile 写回"这些既有基础设施。

## 5. RTL 改动清单

改动已应用在服务器 `/home/rv/work/xs-env/XiangShan`（`git diff` 见 `2-vdot-vv设计与实现/2.2-RTL实现.patch`）。

### 5.1 `yunsuan/src/main/scala/yunsuan/package.scala` —— 新增操作码

```scala
object VipuType {
  ...
  def vmv_x_s = "b01010011".U(OpTypeWidth.W) // vmvxs
  def vdot_vv = "b01010100".U(OpTypeWidth.W) // CIE-2026 custom vdot.vv
}
```

`OpTypeWidth = 8`，取 `0b01010100`（`vredsum` 段之后的空位），不占用任何既有值。

### 5.2 `src/main/scala/xiangshan/backend/decode/VecDecoder.scala` —— 译码入口

```scala
val opivv: Array[(BitPat, XSDecodeBase)] = Array(
  // ===== CIE-2026 自定义指令 vdot.vv : custom-0 opcode = 0x0B, funct7 = 0 =====
  // vd[0] = sum_{i=0..7} sext(vs1[i]) * sext(vs2[i]) , SEW=8, 结果按 32 位写回 vd[0]
  BitPat("b0000000??????????000?????0001011") ->
    OPMVV(F, FuType.vipu, VipuType.vdot_vv, F, T, F, UopSplitType.VEC_VVV),
  ...
)
```

- 用 `BitPat` 直接匹配 custom-0 编码，绕过"指令必须来自 RISC-V 标准指令表"的限制（香山的译码表
  本质是 `BitPat → 译码字段`，`DecodeUnit.scala:814` 把 `VecDecoder.table` 合进全局表）。
- `OPMVV(vdRen=F, fu=FuType.vipu, fuOp=VipuType.vdot_vv, xWen=F, vWen=T, mWen=F, split=VEC_VVV)`：
  不读旧 `vd`（省一次 regfile 读口）、写向量寄存器、不写掩码寄存器。
- `UopSplitType.VEC_VVV`：按 128 bit 粒度拆分微指令。`vl=8, SEW=8` 只需 8 字节，恰好产生 1 个 uop，
  因此每次执行只触发一次点积计算，不需要跨 uop 累加。

### 5.3 `src/main/scala/xiangshan/backend/fu/wrapper/VIPU.scala` —— 数据通路

```scala
// ===== CIE-2026 自定义指令 vdot.vv 的旁路实现 =====
// vd[0] (低 32 bit) = sum_{i=0..7} sext(vs1[8i+7:8i]) * sext(vs2[8i+7:8i])，其余位清零
private val isVdot = fuOpType === VipuType.vdot_vv
// 8 个 int8×int8 乘积符号扩展到 19 bit：|sum| <= 8*16384 = 131072 = 2^17，
// 19 bit 有符号范围 [-262144, 262143] 足够，比朴素的 34 bit 累加窄 15 bit
private val vdotProds: Seq[UInt] = (0 until 8).map { i =>
  (vs1(8 * i + 7, 8 * i).asSInt * vs2(8 * i + 7, 8 * i).asSInt).pad(19).asUInt
}
// 3:2 进位保留加法器（CSA）：输出 (和, 左移一位的进位)
private def vdotCsa(a: UInt, b: UInt, c: UInt): (UInt, UInt) =
  (a ^ b ^ c, Cat(((a & b) | (a & c) | (b & c))(17, 0), 0.U(1.W)))
// Wallace 压缩树：8 个操作数压到 2 个（4 级 CSA），再做 1 级进位传递加法
private val (w0s, w0c) = vdotCsa(vdotProds(0), vdotProds(1), vdotProds(2))
private val (w1s, w1c) = vdotCsa(w0s, w0c, vdotProds(3))
private val (w2s, w2c) = vdotCsa(vdotProds(4), vdotProds(5), vdotProds(6))
private val (w3s, w3c) = vdotCsa(w2s, w2c, vdotProds(7))
private val (w4s, w4c) = vdotCsa(w1s, w1c, w3s)
private val (w5s, w5c) = vdotCsa(w4s, w4c, w3c)
private val vdotSum19 = (w5s + w5c)(18, 0).asSInt
private val vdotResData = Cat(0.U((dataWidth - 32).W), vdotSum19.pad(32).asUInt)

io.out.bits.res.data := Mux(isVdot, vdotResData, vialu.io.out.bits.vd)
```

设计要点：

1. 旁路而非改造 `VIAlu`：`VIAlu` 来自 yuanfudao 团队，是外部依赖（`yunsuan` 子模块）。在 VIPU
   wrapper 层用 `Mux` 覆写输出，既不改上游 IP，也不影响 `vredsum` 等既有指令的行为（`isVdot` 为假时
   等价于原始连线，逐位无差异）。
2. **8 个 8×8 有符号乘法器 + Wallace 压缩树**：`a.asSInt * b.asSInt` 得到 16 bit 有符号乘积，
   符号扩展为 19 bit（位宽由 §6 的范围分析定出，比朴素 34 bit 窄 15 bit），再用 3:2 CSA
   组成压缩树把 8 个操作数压成 2 个，最后做一次进位传递加法。详细对比与实测数据见
   `微架构优化分析.md`（4 个变体的综合单元数 / 最长拓扑路径对比）。
3. `VSew` 无硬依赖：直接从 `vs1/vs2` 的低 64 bit 取 8 个字节，不依赖 `vsew` 动态选择，
   避免给关键路径引入变宽的 mux（这是"快速出功能、后续再优化"的权衡，见第 8 节）。
4. 时序：`VipuCfg` 的 `latency = CertainLatency(2)` 保持不变。逻辑综合口径下本数据通路
   最长拓扑路径 41 级（原串行 34 bit 实现为 50 级，缩短 18%），主要贡献来自位宽收敛
   （50→42 级）与压缩树（42→41 级），乘法器本身约占 30 级、是剩余路径的主体。

## 6. 功能正确性论证（位宽与边界）

| 项 | 分析 |
| --- | --- |
| 单个乘积范围 | `sext8 × sext8` ∈ [−16384, 16256]，16 bit 有符号足够 |
| 8 项和的范围 | 最坏 `8 × (−128 × −128) = 131072 = 2^17`；最坏负值 `8 × (127 × −128) = −130048` |
| 结果位宽 | 17 bit + 符号 → 18 bit 足够；本设计用 **32 bit**，裕量充足（为将来 16/32 元素点积预留） |
| 溢出 | 32 bit 内不可能溢出（最大 131072 « 2^31），无需饱和逻辑 |
| 写回布局 | `Cat(0.U(96.W), sum(31,0))` → `vd[0]` 的 4 个字节（e8 视图下 `vd[0..3]`），其余清零 |
| 与 `vredsum` 的差异 | `vredsum` 读旧 `vd` 累加；`vdot` 不读旧 `vd`（`vdRen=F`），语义更接近"纯函数" |

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 乘法器 + 加法树打散 VIPU 关键路径 | 高频下时序违例 | 本阶段以功能为先。数据通路的位宽与压缩结构见《微架构优化分析》，那里把 34 bit 串行累加换成了 19 bit Wallace 树 |
| `SEW≠8` 时语义未定义 | 与 NEMU 不一致 | 在 NEMU 侧同样按"取低 8 字节"实现；文档明确约束，后续可加 `illegalInstr` |
| `vl>16` 时按 uop 拆分可能重复计算 | 结果错误 | 当前约束 `vl=8`；阶段三在 NEMU/RTL 两侧都限制并要求 `vl≤16`，否则触发 illegalInstr |
| 未使用掩码 | `vm=0` 行为与标准不符 | 文档声明"不使用掩码"；后续可加 `vm=0 → illegalInstr` |
| 与未来 RVV 标准 `vdot` 冲突 | 兼容性 | 已选 custom-0 空间，不存在编码冲突 |
